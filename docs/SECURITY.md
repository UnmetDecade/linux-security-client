# Security model

**English** | [简体中文](SECURITY.zh-CN.md)

## 1. Assets and trust boundaries

Assets that need protection:

- Access tokens, web sessions, and CSRF tokens
- Quarantined files and their hash evidence
- The SQLite database (events, tasks, audits, quarantine metadata)
- Scan evidence and runtime logs
- Scanned files on the host

Trust boundaries:

```
Browser / CLI  ──HTTP──▶  daemon (container)  ──UNIX Socket/subprocess──▶  clamd / freshclam
                                      │
                                      ├──filesystem──▶ /data, /scan
                                      │
                                      └──HTTP (optional, internal network)──▶ docker-proxy ──UNIX Socket──▶ Docker Engine
```

The browser, CLI input, scanned file contents, ClamAV/Falco return values, and container inspect data are all treated as untrusted input. The daemon does not execute shell strings, does not delete automatically, and does not operate containers automatically.

## 2. Authentication and authorization

- Administrator and read-only tokens are generated by the daemon (`secrets.token_urlsafe(32)`) and written to `secrets/*.token` with mode 0600; the token directory is 0700.
- `LSEC_ADMIN_TOKEN` / `LSEC_VIEWER_TOKEN` environment overrides are supported; if they differ from the on-disk files, the token files are atomically replaced with 0600 so the CLI reads the same credentials.
- Bearer tokens use constant-time comparison; after web login, a random session ID and CSRF token are generated.
- Session Cookie: `HttpOnly; SameSite=Strict; Path=/`; with TLS enabled, `Secure` is added.
- Roles: `admin` / `viewer`. All write endpoints check for `admin` on the server side and do not rely on the front end hiding buttons.
- The Falco ingestion token is a separate `integration` role: it is valid only at `/api/v1/integrations/falco` and cannot read status/events/logs; administrator and read-only tokens also cannot write to that endpoint. Ingestion is rate-limited to 240 requests/minute.
- Login is rate-limited by source IP (default 10 requests/minute); exceeding it returns 429.
- Token and session values are not written to logs; login audits record only the role, source, and result. The Falco token path may be shown, but the token contents are never shown or recorded.

## 3. CSRF and browser security

- All write requests on a Cookie session must carry `X-LSEC-CSRF`, whose value comes from the login response and is compared in constant time.
- If a request carries `Origin`, its host must equal `Host`.
- Response headers:
  - `Content-Security-Policy: default-src 'self'; script-src 'self'; ...`
  - `X-Frame-Options: DENY`
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: no-referrer`
  - `Permissions-Policy` disables geolocation/camera/microphone
- The front end loads no third-party scripts, fonts, or CDNs; the CSP's `style-src` allows inline style attributes only for first-party-generated progress bar widths/spacing.
- All dynamic text in the web UI is HTML-escaped before insertion; `innerHTML` is not used to concatenate unescaped data.

## 4. Command execution

- All external commands are executed through argv lists; `shell=True` is forbidden.
- Subprocesses use `start_new_session=True`; on timeout the entire process group is killed.
- Output has a size limit; logs/APIs never return unbounded output.
- ClamAV uses the documented clamd UNIX Socket protocol, with commands and responses framed by NUL (`zPING`, `zVERSION`, `zSCAN path`, `zSHUTDOWN`), rather than parsing human-oriented CLI output.
- clamd commands reject paths containing newlines/NUL; path validation happens before the protocol terminator is appended.
- Lynis is invoked only as `audit system --quick --no-colors --quiet` plus report/log output paths; it does not execute suggestion text and does not accept arbitrary user-supplied arguments.
- `yarac` receives only the rule files from this installation and the compile output path; `yara` receives only compiled rules and target files inside the allowlist; arguments are batched under a 128 KiB argv budget.
- `sigtool` is invoked only as `--info=<CVD path>` to read signature metadata; it does not execute database contents.
- The host security audit is entirely read-only: it writes no system files, changes no sysctl, starts/stops no services, and modifies no accounts or firewall.

## 5. File and path security

- All user-supplied paths must be absolute, at most 4096 characters, and contain no NUL/newline/carriage return.
- Custom scan paths must be inside `scan.allowed_roots`.
- Quarantine/restore paths must be inside `response.quarantine_roots`.
- The quarantine source must be a regular file; symlinks, directories, devices, and FIFOs are rejected outright.
- Quarantine opens with `O_NOFOLLOW`, and the original file is deleted only after copying and hash verification; `(st_dev, st_ino)` is compared before deletion.
- Restore refuses to overwrite an existing original path and re-verifies the hash after writing.
- File traversal does not follow symlinks; it skips `/proc`, `/sys`, `/dev`, `/run`, the container data directory, the ClamAV database, and the data volume.
- The quarantine directory is 0700 and files are 0600.
- YARA rule packs accept only regular files/directories inside `yara.inbox_dir`; symlink sources and symlinks, `..` traversal, and absolute path entries inside the zip are rejected.
- Each rule file is verified one by one against the manifest's SHA-256; an existing same version is refused; the activation pointer is updated atomically using a temporary file plus `os.replace`.
- Wazuh alert files and state files use `O_NOFOLLOW`; `client.keys` contents are never read; the state directory is 0700 and the state file is 0600.

## 6. Data and logs

- SQLite enables WAL, foreign keys, and busy timeout; migrations run inside explicit transactions, and a failure rolls back and restores the pre-migration backup.
- The data directory defaults to 0750; token/evidence/quarantine directories are 0700.
- Logs are JSON lines with rotation (default 10 MB × 5); no tokens, Cookies, CSRF values, or file contents are recorded.
- Audit records include the request ID, before/after state (truncated at 16 KB), and confirmation flag, and cannot be modified or deleted by ordinary users.
- Event evidence `details` are limited to 32 KB and truncated beyond that.
- The audit evidence directory is 0700, and `report.json`, Lynis reports, and logs are 0600; report reads are capped at 1 MB.
- The audit does not read or store password hashes from `/etc/shadow`; it only determines whether the password field is empty.

## 6.1 Container and Falco data handling

- The Docker API client implements GET only; no start/stop/restart/exec methods exist in the code, and the proxy also rejects write methods.
- Container IDs must match 12–64 hex characters; the proxy accepts inspect paths only in that format, preventing path injection.
- Inspect responses are capped at 8 MB; the container count is limited by `max_containers`; output fields are truncated.
- **Container environment variables are not stored** (`Config.Env` often contains credentials); tests explicitly verify that environment variables never appear in results.
- Container risk events store only the rule, image, state, and bounded check details, not the full inspect document.
- Falco events are limited by `max_event_bytes` (default 32 KB) and only allowlisted fields are extracted; an invalid container ID is not used as the target ID.
- Command output in Falco events enters the event evidence and may contain sensitive information; event center access is role-controlled, and export requires login.
- lsec does not install, start, or load the Falco driver, nor modify kernel parameters; the install plan is text advice only.

## 6.2 YARA rule packs

- **Trusted source**: rule packs are read only from the administrator-controlled inbox; lsec does not download rules.
- **Integrity**: the manifest must list every rule file and its SHA-256; any undeclared file, hash mismatch, or missing file causes the whole pack to be rejected.
- **Authenticity**: when `require_signature=true`, OpenSSL verifies the detached `manifest.sig` over the manifest bytes; a missing public key or invalid signature rejects the installation—there is no "install first and check later".
- **Compilability**: only a successful `yarac` compile produces an activatable version on disk; compile errors are included in the API error and audit.
- **Immutable versions**: the `<pack_id>/<version>` directory is written once and never overwritten in place; both deletion and activation require confirmation and are audited.
- **Scan boundaries**: only regular files inside `scan.allowed_roots` are enumerated, and symlinks are not followed; target paths in the output must lie within the current scope, otherwise the hit is discarded.
- **False positives and boundaries**: a rule hit is a rule-match result, not equivalent to a malware conclusion; severity comes from rule tags, defaulting to medium.

## 6.3 Wazuh local integration

- lsec does not contact the Manager, register Agents, or read/forward registration key contents.
- Only new lines from the local `alerts.json` enter the event center; on first enable it starts at EOF, avoiding import of the historical backlog.
- Per-read and per-event sizes are bounded; an oversized line is continuously discarded up to the next newline, and a truncated fragment is never parsed.
- Level and group tags are mapped to unified severity/category; evidence retains the alert id, rule, Agent, Manager name, and bounded raw text.
- `manager_connection_verified` is always false; the capability state is at most `degraded` and never shown as "Wazuh fully in control".
- Alerts never trigger automatic quarantine, deletion, or container operations.

## 7. Container hardening

`docker-compose.yml` defaults:

- Does not mount `/var/run/docker.sock`
- Does not use `network_mode: host`, `pid: host`, or `privileged`
- `no-new-privileges:true`
- Mounts only the data volume, virus database volume, and explicitly configured scan directories
- Ports are published to host `127.0.0.1` by default
- Log rotation limits

### 7.1 Container monitoring proxy (optional)

`docker-compose.container.yml` adds a separate `docker-proxy`:

- The lsec container still does not mount the Docker Socket; only the proxy mounts `/var/run/docker.sock:ro`
- The proxy allows only 4 GET endpoints, returns 403 for other paths and 405 for non-GET methods; responses are capped at 8 MB
- The proxy joins an `internal: true` network and publishes no host ports; lsec reaches it through the internal DNS name `http://docker-proxy:2375`
- `cap_drop: ALL`, `no-new-privileges:true`, `read_only: true`, with only `/tmp` as a small tmpfs
- The proxy runs as root to read the Socket; it remains a highly privileged component and is **not** a risk-free component

> The Docker Socket is equivalent to host root. The proxy's allowlist reduces misuse and write-operation risk, but it cannot eliminate the residual risk that "whoever controls the proxy image/container controls the host". The proxy image and Compose files must be treated as trusted infrastructure.

**Residual risk**: the in-container process runs as root so it can read and quarantine arbitrary files in mounted directories. Therefore:

- Anyone who can control the container or image has root privileges over those mounted directories
- Mount only the paths that need checking in the scan directories where possible; do not mount `/`, `/etc`, user home directories, or credential directories
- Treat images and Compose files as trusted infrastructure; do not hand the Docker Socket to the lsec container

## 8. Transport security

- By default, 8080 is published only to the host loopback address; SSH tunneling is recommended for remote access.
- Direct LAN access requires explicitly setting `LSEC_LISTEN_ADDR=0.0.0.0`; without TLS, token transport is insecure in that case.
- Production should terminate TLS at a reverse proxy, or configure `server.tls_cert` / `server.tls_key` (TLS 1.2+, HSTS enabled).
- The daemon refuses to start without TLS on a non-loopback address unless configuration allows it or `LSEC_ALLOW_INSECURE_REMOTE=1` is explicitly set. In the container it starts with that explicit switch, and the actual exposure is controlled by port mapping.

## 9. Updates and supply chain

- The ClamAV virus database is updated from the official mirror through the distribution-provided `freshclam`; freshclam performs CVD signature verification during download. After each update, lsec re-checks the on-disk `.cvd` file with `sigtool --info` and parses `Verification OK`; unverified (sigtool missing or only `.cld`) is explicitly shown as "unverified/not applicable" and never treated as passed.
- YARA rule packs must be placed and signed by an administrator; lsec does no online rule subscription.
- Image builds depend on the Debian package repositories and the Docker Hub `python:3.12-slim-bookworm` image; production should pin image digests, use an internal registry, and run vulnerability scanning.
- deb release artifacts include `lsec_<version>_all.deb`, the source package, and `SHA256SUMS`; `scripts/build-release.sh --sign-key <KEYID>` generates detached GPG signatures, and `scripts/verify-release.sh` re-verifies the checksums and signatures.
- Automatic updates do not overwrite the program itself; container upgrades rebuild the image, host upgrades install a new deb with `apt install`/`dpkg -i`, and old versions can be rolled back (see the deployment document).
- The systemd unit enables `NoNewPrivileges`, `ProtectSystem=strict`, `RestrictAddressFamilies`, and an empty capability set by default, and permits writes only to `/var/lib/lsec`, `/var/log/lsec`, and `/run/lsec`.

## 10. Known residual risks

| Risk | Description | Mitigation |
| --- | --- | --- |
| Root inside the container | Needed to read/move mounted files | Minimize the mount scope; do not mount the Docker Socket; treat as trusted infrastructure |
| No real-time protection | fanotify is not enabled in the container | The UI explicitly shows `unsupported`, and the overall status is "protection incomplete" |
| No automatic response | Design choice | All quarantine/restore/delete require manual confirmation |
| Plaintext HTTP | Loopback by default; direct LAN access requires explicit enablement | SSH tunnel / TLS reverse proxy / configure certificates |
| Single node | No central management server | Back up `/data`; can be extended in a later phase |
| Limited ClamAV detection | A limitation of the signature engine itself | Does not claim 100% protection; results represent only what the engine actually returns |
| Limited audit scope | The container sees only its own mounts, network namespace, and kernel parameters | The UI/evidence explicitly marks `scope_note`; container results are not treated as a full host audit |
| Lynis warnings are not vulnerability conclusions | Warnings are configuration/runtime state hints, and severity is mapped by fixed rules | The report retains raw evidence; does not claim the host is compromised |
| Docker proxy is highly privileged | The Socket equals host root; the proxy cannot eliminate the risk once controlled | Separate container, GET allowlist, read-only root filesystem, cap_drop ALL, internal network; no external port publication |
| Container checks are heuristic | They check configuration only, not image vulnerabilities or runtime behavior | The UI states this explicitly; risk level is not a vulnerability score; no automatic response |
| Container inventory is Docker only | Containerd is probed only, with no inventory collection | The inventory and scope notes explicitly state the source; Docker data is not passed off as containerd |
| Falco runtime state unverified | lsec cannot confirm the host-side process or rule loading | `running_verified=false`; capability state and runtime state are shown separately; never shown as protected |
| YARA rule quality | Rule hits depend on the rules an administrator deploys and signature trust | Mandatory SHA-256 + optional signatures; immutable packs; events retain the rule and pack version; does not claim complete malware detection |
| Wazuh Manager unverified | lsec can see only the local Agent and local alert file | Capability state is at most `degraded`; the UI always shows "Manager connection unverified"; no Manager API provided |
| Rule scanning resource consumption | Large directories + complex rules may consume CPU/IO | Batching, timeouts, administrator-initiated only; no resident real-time rule monitoring |
| CVD signature re-verification depends on sigtool | Some distributions/minimal images may not have it installed | Explicitly shown as "unverified"; freshclam's built-in verification still runs during download |
